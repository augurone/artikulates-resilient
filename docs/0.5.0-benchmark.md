# Resilient 0.5.0 benchmark

Version 0.5.0 is complete when Resilient can provide reliable, reusable
project-aware analysis for the native-JavaScript conventions already used in
the Artikulates codebase.

The benchmark is an acceptance bar, not a promise to reproduce TypeScript.
It measures whether the analysis has the right context, preserves legitimate
unknowns, identifies contradictions when evidence exists, and remains useful
through the ESLint developer workflow.

When this benchmark passes, a functional shell in a shared module enforces its
contract at every statically reachable, supported call site in the Active Tree.
This supplies the coordination guarantee teams commonly seek from TypeScript
interfaces, derived from executable code rather than a parallel annotation
layer.

## Release outcome

Given one or more source roots, Resilient produces a deterministic analysis
snapshot containing:

- the exact Active Tree;
- resolved, unresolved, and unsupported module edges;
- contracts and diagnostics for active files;
- enough source/provenance information for ESLint to surface the result;
- invalidation information when project inputs change.

The Project Tree may index unused files, but unused files do not become
semantic input merely because they are present.

## Acceptance benchmark

### 1. Active Tree correctness

Use a fixture project containing:

- an active root importing a provider;
- a re-export barrel and a transitive leaf;
- an unused source file;
- an unresolved external or dynamic edge;
- a file that is available but not reachable from the selected root.

The result must prove that:

- the root, provider, barrel, and leaf are active;
- the unused and unreachable files are indexed but inactive;
- the unresolved or unsupported edge is recorded as unknown;
- no diagnostic is emitted from an inactive file;
- every active file is reachable through a recorded edge.

### 2. Residual contract preservation

Use real patterns from `artikulates`, including:

```js
const {
    bgAttrs = '',
    bgStyleStr = '',
    inlineStyle = {},
    ...style
} = backgroundConfig(background);

const combinedStyle = {
    ...style,
    ...inlineStyle
};
```

and:

```js
const {
    applyToParent = false,
    ...typeSettings
} = typography;
```

The analyzer must:

- represent `style` and `typeSettings` as residual object contracts;
- record that extracted keys are excluded from the residual;
- preserve the residual through aliases, calls, returns, imports, and spreads;
- preserve spread order and later explicit overrides;
- allow a later property demand to resolve when evidence exists;
- remain unknown for a residual property for which no evidence exists;
- avoid treating object rest as an array, arbitrary unknown value, or error.

Here “object rest” means an object-pattern `RestElement` such as `...style`.
Array-pattern rest elements remain array-shaped contracts and are not residual
object contracts. A known residual property is checked like any other known
property; only properties without evidence remain unknown.

Also cover residual reification behind a lexical property:

```js
return { args, [lexicalName]: renderProps };
```

If the key is known, the property must be discoverable. If it is dynamic, the
value remains an open object contract without inventing a property name.

These are residual-contract acceptance cases, not the current shared benchmark
fixture inventory. The representative executable regression cases live in
`tests/project-tree.test.js`; `scripts/benchmark.js` currently benchmarks
project activation, invalidation/reuse, shared providers, runtime boundaries,
and ESLint agreement separately. The benchmark output must not be read as
claiming that the residual examples above are part of that fixture run.

### 3. Invalidation and reuse

Starting from the same project snapshot:

- changing an active leaf invalidates that leaf and affected dependents;
- changing an inactive file does not change the active result;
- changing a barrel invalidates its importers;
- changing parser/config/resolver identity invalidates affected analysis;
- unchanged files can reuse their parsed and analyzed state;
- recomputation produces the same contracts and diagnostics as a clean run.

The benchmark should report both the invalidated set and the final Active Tree.

### 4. Snapshot and ESLint agreement

The public contract API and ESLint rules must consume the same analysis result.
For each fixture:

- direct API diagnostics and ESLint diagnostics agree in rule identity,
  location, and count;
- diagnostic ordering is deterministic;
- contract facts remain inspectable without requiring an editor adapter;
- ESLint does not implement a second inference path.

The consumer does not manage project activation. On the first contract-rule
invocation in an ESLint run, Resilient activates its internal project analysis
for the current root and supported local dependency closure. Subsequent
contract rules reuse that analysis state; the lifecycle is covered by a cache
build-and-hit acceptance test.

### 5. Shared provider enforcement and 0.4.3 regression

The core form of this behavior already exists in 0.4.3: imported functions,
barrels, default values, return contracts, call-site contradictions, and
dependent invalidation are already part of the contract graph. This section is
therefore both a regression benchmark and a promotion benchmark. Version
0.5.0 must preserve the behavior while making the Active Tree explicit and
adding residual contracts and reusable analysis snapshots.

Use a fixture project containing a shared provider module and two or more
consumer files that import and call it:

```js
// providers/items.js
export const getItems = ({ items = [], label = '' } = {}) => ({ items, label });
```

```js
// consumer-a.js
import { getItems } from './providers/items.js';
getItems({ items: 'not-an-array', label: '' }); // contradiction
```

```js
// consumer-b.js
import { getItems } from './providers/items.js';
getItems({ items: [], label: 42 }); // contradiction
```

The result must prove that:

- both contradictions are reported at their respective call sites;
- valid call sites in other consumers produce no diagnostic;
- changing the provider shell's signature invalidates all importers and
  re-checks them against the new contract;
- the executable function signature, defaults, operations, and return behavior
  together form the authoritative contract; no annotation is required;
- the provider contract is inspectable through the public snapshot API without
  an editor adapter.

This is the coordination guarantee: for supported native-JavaScript
boundaries, a functional shell can replace a separately maintained TypeScript
interface for cross-file enforcement. The shell remains the runtime
implementation, and its defaults provide canonical empty values.

### 6. Runtime-boundary degradation

Use a fixture in which data enters through an external or otherwise
unresolved boundary and becomes usable only after an explicit normalizer:

```js
const raw = await externalSource();
const normalized = normalize(raw);
render(normalized);
```

The result must prove that:

- `raw` remains unknown at the external boundary;
- `normalize` establishes a known contract when its implementation is
  available to analysis;
- downstream operations are checked against `normalized`;
- invalid input follows an explicit fallback or failure path;
- Resilient does not claim that static analysis validated the external data
  itself.

This preserves the boundary distinction: Resilient can guarantee the contract
of the code handling data, but it cannot make external data trustworthy by
static analysis alone.

### 7. Performance baseline

Record cold and warm timings on the supported Node versions for two workloads:

- a shared Active Tree workload that both 0.4.3 and 0.5.0 can analyze;
- a 0.5.0 Project Tree discovery and incremental-analysis workload.

For the shared workload, the 0.5.0 implementation must not introduce more
than a 20 percent cold or warm regression against the equivalent 0.4.3
baseline, measured with the same fixture and command. The Project Tree
workload establishes its own baseline and must report its discovery and
incremental costs rather than being compared to work 0.4.3 did not perform.

The benchmark must report:

- files indexed;
- files activated;
- files parsed;
- files re-analyzed after a change;
- cache hits and misses;
- diagnostic count.

The repository runner is `npm run benchmark`. It emits JSON for the current
Node process, including the shared Active Tree workload, Project Tree
discovery/invalidation timings, cache reuse, and direct API versus ESLint
diagnostic agreement. It also reports two uncached graph-only timing samples
for orientation. Those samples exclude Project Tree activation, snapshot, and
invalidation work, so they are not a regression percentage or a substitute for
the eventual 0.4.3 comparison gate.

The numbers are evidence about the implementation, not correctness claims
about arbitrary repositories.

No real-project 0.4.3 comparison is committed here. A previous local baseline
included environment-specific paths and package-state notes that no longer
describe this stack, so it was removed. The 20 percent gate remains an
end-to-end measurement requirement: run the same project, command, Node
version, and repeated-run method for 0.4.3 and 0.5.0 before making that claim.

## 0.5.0 implementation status

1. **Benchmark scope.** The coverage qualification, boundary distinction, and
   0.4.3 regression scope are explicit.
2. **Fixture coverage.** Shared providers, barrels, active-set boundaries,
   and runtime boundaries are covered. A real-project performance comparison
   remains a separate release-gate measurement.
3. **Residual semantics.** Object-rest binding, exclusion sets, open-object
   state, spread ordering, and lexical reification are implemented and covered
   by representative regression tests; they are not part of the shared
   benchmark fixture run yet.
4. **Explicit tree state.** Project Tree indexing and Active Tree activation are
   exposed while the existing on-demand ESLint path remains available.
5. **Shared snapshot boundary.** ESLint consumes the same contract graph exposed
   through the contracts API, with clean-run equivalence coverage.
6. **Invalidation and reuse.** Changed leaves, providers, inactive files, and
   configuration identities are covered; invalidation, reuse, and first/repeat
   measurements are reported.
7. **Release preparation.** Package promotion and final artifact verification
   remain release operations, not analysis capabilities.

## Not part of 0.5.0

- no annotations or new source language;
- no TypeScript compatibility layer;
- no requirement for an LSP or editor extension;
- no whole-project semantic activation;
- no guessed contracts for dynamic or unresolved edges;
- no claim that static contracts make external data trustworthy without a
  runtime boundary policy.
